# 01 原理详解：从 Mali 驱动漏洞到持久化 root

> 本文回答"为什么可行"，与 `02-复刻手册.md`（"怎么做"）配对阅读。

## 0. 攻击面总览

```
用户进程 (shell, uid 2000)
   │  open("/dev/mali")          ← 权限 0666，任意进程可打开（Android TV 固件通病）
   ▼
mali.ko (内核驱动, Mali-450 Utgard, DDK r5p0 系)
   │  ioctl 0xc0188404 = pp_and_gp_start_job  ← 提交 GPU 作业
   ▼
Mali-450 GPU 硬件
   │  按 job 描述符执行：读纹理(采样) / 写帧缓冲(WB0 回写)
   ▼
物理内存  ←★ GPU 是 DMA 主设备，绕过 CPU 的所有保护（无 PAN/无 SMMU 隔离）
```

**核心思想：GPU 是一个可以直接读写物理内存的"自由员工"。** 内核驱动对提交的 job 几乎不做校验（漏洞），于是我们把内核内存"伪装成纹理"让 GPU 读回来（读原语），或把 WB0 输出指向内核内存（写原语）。

## 1. 漏洞：`mali_mem_validation_check` 是空函数

反汇编 `mali.ko`（带符号版本 91624 行 / 内置符号 84092 行的 2018 构建 `3.14.29-g4f3e19b`）：

```
mali_mem_validation_check:
    mov w0, #0
    ret
```

这个函数本应校验用户态提交的物理地址合法性（白名单/范围检查）。它直接返回 0（通过）。后果：**`mali_mem_bind` (ioctl `0xc0288302`) 可以把任意物理地址绑定进当前 GPU 会话的页表**，参数结构：

```c
struct mali_bind {          // 40 字节
    uint64_t ctx;
    uint32_t vaddr;         // GPU 虚拟地址
    uint32_t size;
    uint32_t flags;         // 0x200 = dma-buf 句柄绑定；0x800 = 裸物理地址绑定(flags=BIND_EXTERNAL)
    uint32_t padding;
    uint32_t phys_addr;     // ← 任意物理地址
    uint32_t rights, ext_flags, pad2;
};
```

注：本机 ABI 与 Mali DDK 官方头文件有出入——`pp_and_gp_start_job` (0xc0188404) 是 24 字节指针信封 `{ctx, *gp_job(104B), *pp_job(408B)}`，通过 hook 抓真实流量 + 反汇编 dispatch 表确认（见 `evidence/analysis/mali_ioctl_disas.txt`）。

## 2. 写原语：让 GPU 把数据"画"到内核内存

PP（像素处理器）job 完成时按 `WB0`（write-back 0）配置把结果写进内存。PP job 的 408 字节 uargs 里：

| uargs 偏移 | 字段 | 作用 |
|---|---|---|
| 0x08 | user_job_ptr | 随意（通知用） |
| 0xa8 | wb0 寄存器组 | 0xac = WB0 目标物理地址 ★ |
| 0x14 | frame_registers | reg[1]=renderer list 指针, reg[8..] 等 → 写入 PP 硬件寄存器 |
| 0x170 | num_memory_cookies | 置 0（跳过 DDK 内存 cookie 校验） |
| 0x190 | 通知指针 | 完成时写入的值 |

内核提交函数（反汇编 `pp_job_start.txt`）在 flags bit2=0 路径上写入 `reg0=0xFFF00000`，然后把 `frame_registers[1..11]` 原样拷入 PP 寄存器 0x04..0x2C。所以**手搓一个 408 字节 job + MEM_BIND 把 carveout 页绑到 WB0 目标 VA**，即可让 GPU 把 128 字节（像素格式 0x06：16×8 字节重复）的画布"画"到任意 8 字节对齐的物理地址。

写入值 = 画布里的常量色 → **一次写 128 字节同一个 u64 重复 16 次**。要写不同值就分多次（或 8 字节对齐的槽位数组一次填同一指针）。

工具：`tools/bin/gpu_arb_write`（源码 `tools/src/gpu_arb_write.c`）。用法：
```
gpu_arb_write <phys_hex> <value_hex64>     # 128B 全部写 value
gpu_arb_write 0 0                          # 自校准（写 carveout 测试页）
```

## 3. 读原语：让 GPU 把内核内存"采样"出来

这是本项目最难、也是最有创造性的部分。难点：**没有 shader 编码器，无法手写 Mali Utgard ISA**（历次手逆全部失败，见 RESEARCH_NOTES.md）。

### 3.1 突破口：不逆编译器，抄真实作业

用 `LD_PRELOAD` hook（`tools/src/hook.c`）拦截 `/dev/mali` 的 ioctl 和 mmap，在自己进程里跑一次真实 GLES（`gles_probe.c`：pbuffer + 四种 draw，其中 draw3 是纹理采样），把 DDK 提交的 **GP/PP job 结构体 + GPU 窗口内存**原样 dump 出来。

关键发现（抓包见 `evidence/captures/`）：
- DDK 通过 `mem_write_safe` 上传的纹理不在 mali mmap 窗口里，但**纹理所在的 GPU VA（0x10040000）可在运行时通过第二次 mmap 窗口拿到**；
- varying 缓冲（uv 四顶点浮点）在窗口 1 内固定偏移 0x2b280，**patch 它就能控制 GPU 采样纹理的相位**——这是密集读的基础；
- PP job 完全可以脱离 GP 单独提交（varyings/tile list 已在克隆窗口里）。

### 3.2 回放实验（决定性验证）

`replay.c`：ion 分配两块内存 → 内容 = 抓到的 win1（0x40000，命令流/tile/varyings）+ win2（0x4000，纹理）→ MEM_BIND 到原 GPU VA → 原封不动重放抓到的 PP job（只改通知指针、WB0 目标指向自己的 carveout 页）。

结果：**GPU 执行了完整流水线，把纹理采样结果 1KB 写进我们的缓冲**，内容与源纹理逐像素对应。读原语成立。

### 3.3 任意地址读

1. `bind_ext(0x10040000, 0x4000, <内核物理地址>)` —— 把 16KB 内核内存绑到"纹理"的 GPU VA；
2. 重放 PP job → GPU 把内核内存当纹理采样 → 输出 1KB（256 个 u32，采样点固定在纹理内 offset ≡ 0x20 (mod 0x40) 处）；
3. **密集读**：patch win1 克隆里 0x2b280 处的 uv 四顶点（16 个相位 sx,sy∈0..3），每个相位得到 256 个不同 offset 的样本 → 16 相位拼出完整 16KB（`host_dense.py` 自动调度 + 字节重排 + 缺口检测）。

两个必须知道的映射（校准数据在 `evidence/kallsyms/win2.bin`）：
- 输出 u32 的字节序是 `(k2,k1,k0,k3)`（GPU 采样通道序），拼装时需重排；
- 采样 texel = `sx + 4*px`（px = 输出像素列），角点 uv = `sx/64 + {0,1}`，**没有 0.5 像素中心偏移**（校准实测，与预想不同）。

### 3.4 找内核符号：全镜像扫描 + kallsyms 重建

- 已知 `_text` 物理 = `0x1080000`（VA `0xffffffc001080000`，内核 Image 头部自引用地址验证）；
- 用 gpu_scan 扫 `0x1080000~0x2030000`（16.4MB，1004 块 × 16KB，约 3 分钟）；
- 在扫描数据里找**升序内核指针数组** → 命中 `kallsyms_addresses` @ 物理 `0x1ae5d00`（84092 项，首项 = `_text`）；
- 密集读数组 + names 压缩流（`0x1b8a200` 起）+ token 表（`0x1c82d00`，null 结尾 256 字符串）→ 完整重建符号表；
- **验证**：解码结果与设备 `/proc/kallsyms` 前 84092 条逐条比对，0 mismatch。

最终常量（详见 `04-设备事实与常量.md`）：

| 符号 | VA | 物理地址 |
|---|---|---|
| kallsyms_lookup_name | ffffffc00111ec70 | 111ec70 |
| sys_call_table | ffffffc001f2b000 | 1f2b000 |
| memcpy | ffffffc0013e4400 | 13e4400 |
| selinux_enforcing | ffffffc00211f77c | 211f77c (.bss) |
| core_pattern | ffffffc001f613c8 | 1f613c8 |
| sys_ni_syscall | ffffffc0010c39e0 | — |

## 4. 任意内核函数调用：sys_call_table 空槽劫持

`sys_call_table[244..259]` 共 16 项全是 `sys_ni_syscall`（未实现的系统调用）。用写原语把 128 字节（=16 个 u64）填进 `[246]` 起的槽位（**别碰 244=accept4、245=recvmmsg**）：

```
gpu_arb_write 1f2b790 ffffffc0013e4400   # 16 个槽全变成 memcpy
```

然后 64 位进程（`kfunc246`，aarch64 静态）调用 `syscall(246, dst, src, len)` → 内核派发到 **memcpy(dst, src, len)** → 任意内核内存读/写（包括把字符串写进 .data）。

注意：32 位进程走 `compat_sys_call_table`（在 .text，别动），我们改的 arm64 表只影响 64 位进程——这反而降低了破坏面。

## 5. 提权闭环：core_pattern 管道劫持

SELinux 先清零（memcpy 写 `selinux_enforcing=0` → Permissive），然后：

1. `memcpy(core_pattern, "|/data/local/tmp/roothelper.sh", 31)` —— Linux 内核在进程崩溃转储时，若 core_pattern 以 `|` 开头，会以 **uid=0 + 完整 capabilities + kernel:s0 上下文** 执行该程序；
2. 触发崩溃：`ulimit -c unlimited; kill -SEGV $$`；
3. roothelper.sh 以真 root 运行：装 su（`mount -o rw,remount /system; cp su /system/xbin/su; chmod 6755`）、设 `service.adb.tcp.port=5555`、执行 `/data/local/tmp/root_cmd.sh`。

为什么绕这么大弯：**adb shell 的进程树 bounding set 只有 0xc0（SETGID|SETUID）**，su 即使 setuid 成功也拿不到 CAP_DAC_OVERRIDE，很多操作会莫名 "Permission denied"。kernel 上下文 CapBnd = 0x1fffffffff（全量），才配叫真 root。经验法则：
- su：够用来 cat/ps/reboot/读 /proc；
- 写文件/remount/dd/chmod 别人拥有的文件：**一律走 roothelper 通道**。

## 6. 持久化：三层防线

内核态（slots、core_pattern、SELinux 状态）重启即失，因此持久化分三层：

| 层 | 机制 | 效果 |
|---|---|---|
| **L1 内核补丁**（根基） | boot.img 内核里 `sel_write_enforce`（VA 0xffffffc001385f08）改为 `mov w0,#0; ret`（7 字节差异）。init 开机调 `setenforce(1)` 变成空操作 → **每次开机 SELinux 自动 Permissive** | su 的 setuid 提升不再被 secureexec 剥夺；一切 SELinux 拦截失效 |
| **L2 开机钩子** | `/system/bin/install-recovery.sh` 末尾追加 `( /system/bin/rootify.sh ) &`（flash_recovery 服务开机以 root 跑） | rootify.sh 重跑 gpu_arb_write 恢复 slots、写 persist.adb.tcp.port=5555（实测生效） |
| **L3 手动恢复** | 任何时刻按 `02-复刻手册.md` §6 重跑写入链 | 30 秒恢复全部内核态 |

**为什么 L1 是根基**：SELinux Enforcing 时，内核对 setuid-root exec 施加 secureexec（因 shell 域无 `noatsecure` 权限），euid 提升被剥夺——su 完全失效。Permissive 是 su 可用的前提。

**内核补丁安全性**：原厂 Image 与补丁 Image 全量 diff 仅 7 字节（`mov w0,#0; ret` 与原指令恰好 1 字节相同）。ramdisk/DTB 未动，stock recovery 分区未动。刷写失败的最坏情况用 `images/boot_backup.img` dd 回去（需 adb 可用，所以**恢复出厂永远可行：adb 不会因 boot 补丁消失**）。

## 7. 为什么这么曲折：已被证伪的路径

详见 `RESEARCH_NOTES.md`（时间线）与 `03-踩坑清单.md`。要点：

- ❌ 手写/逆向 Mali Utgard shader ISA —— DDK 编码器无公开实现，Lima ISA 不通用，全部失败
- ❌ 从 libMali.so 抄现成 shader 字节 —— 0xB8000000 全区 0 命中
- ❌ 找 1275 固件包取常量 —— 用户拿到的 T50A 包是 MStar 平台另一机型
- ❌ MMU 页表 dump ioctl —— GPU 挂起时 MMU 寄存器读失败，走不通
- ❌ su 直接干一切 —— bounding set 0xc0 限制（见 §5）
- ✅ 回放真实 DDK 作业 —— 唯一走得通的路，也是本项目的核心方法论
