# 03 踩坑清单（现象 → 原因 → 对策）

> 全部为本项目实测踩到。按"伤害程度"排序。**每一条都真实消耗过时间，接手前通读一遍。**

## A. 会炸电视的

### A1. 对已绑定的 GPU VA 重复执行 mali_mem_bind → 内核 panic（重启）
- **现象**：一个进程里第二次 `bind_ext(同一 VA, ...)`，电视直接重启（uptime 归零）。全镜像连续扫描第一次跑炸就是这个。
- **原因**：`mali_mem_mali_map_prepare` 对已有映射的 VA 重复 prepare 返回错误，内核走上异常路径。另有 timeline 相关 panic（抓来的 job 里 fence 点是原会话状态：`Mali Timeline: point 2 is not valid`）。
- **对策**：
  1. **同一 VA 永远只绑一次**。gpu_arb_write 的校准用 EXT_VA(0x40000000)、目标写用 WB_VA(0x40002000)——两个窗口分开（tools/src/gpu_arb_write.c 已修复）。
  2. 抓来的 job 重放前**清零 fence 字段**（pp+0x170 cookies、fence 相关段），否则第一次能跑、第二次必炸。
  3. 改绑物理地址做扫描时，**每块开新的 /dev/mali 会话**（绑定一次用完即弃）——host_scan.py 的做法。
  4. 批量 job 之间 `usleep` 几毫秒让 timeline 排空。

### A2. 内核 memcpy 写到无效地址 → panic 重启
- **现象**：kfunc `zero 211f77c 4`（少了内核基址）→ 电视重启。
- **原因**：slots 已指向真 memcpy，参数 0x211f77c 是未映射的用户地址，内核裸 memcpy 触发 oops。
- **对策**：kfunc 的地址参数**必须传完整 VA**（`ffffffc00211f77c`），写脚本前逐字核对。

### A3. carveout 堆耗尽
- **现象**：`ION_IOC_ALLOC` 失败，"heap exhausted"。
- **原因**：被杀进程泄漏绑定引用，ion carveout 池耗尽。
- **对策**：`reboot`（唯一可靠清理方式），重启后重跑。

## B. adb / 连接类

### B1. adb 命令报 "failed to get features" 或 clang 报 temp 权限错误
- **原因**：默认 `%TEMP%`（AppData）目录对沙箱/权限受限进程不可写，adb.log 写不进去。
- **对策**：每个 shell 会话开头 `export TEMP="$PWD/tools/tmp" TMP="$PWD/tools/tmp"`（tools/tmp 已建好）。

### B2. adb 频繁掉线 / device offline
- **现象**：电视活着（ping 通）但 adb offline；长命令跑到一半断。
- **原因**：电视待机（Wi-Fi/TV 休眠）；或 adbd 被系统杀。
- **对策**：写重试循环（`for i in ...; do adb connect ...; sleep 5; done`）；**长任务一律设备侧脱离 + 事后收结果**（输出写文件）。本机验证：adb 是 TV 系统设置里开的网络调试，重启后自动恢复。

### B3. adb shell 长输出被截断 / 后半段丢失
- **现象**：一条长命令链的输出只有前半截。
- **原因**：进程被 kill 后输出缓冲丢失；或连接中断。
- **对策**：关键输出重定向到设备文件，`adb shell "cat 文件"` 单独读。

## C. shell / 文件操作类

### C1. ★ mksh heredoc 会静默截断目标文件
- **现象**：`adb shell "cat > file <<EOF ... EOF"` 后文件变成 **0 字节**（或部分内容）。
- **原因**：Android 的 mksh 实现 heredoc 先打开重定向目标再写临时文件；临时文件创建失败（/data/local 不可写）时**目标已被截断**。曾把 roothelper.sh 清成 0 字节，导致 coredump helper 变成空脚本（dmesg: `Core dump to |... pipe failed`）。
- **对策**：**写设备文件一律 `adb push`**，永远不用 heredoc。需要生成设备侧脚本时在 PC 侧写好再 push。

### C2. uid=0 却 Permission denied
- **现象**：`su -c 'touch /data/local/tmp/xxx'` 失败，`su -c id` 明明显示 uid=0(root)。
- **原因**：adbd 进程树的 **bounding set 只有 0xc0**（CAP_SETGID|CAP_SETUID），没有 CAP_DAC_OVERRIDE/CAP_FOWNER。/data/local/tmp 的属主是 shell，uid=0 属于 "other" 类，无 caps 就写不进。同理 /system/bin 下的文件也改不动。
- **对策**：写 /data/local/tmp 之外的文件、remount、dd、chmod 他人文件 → **走 roothelper（kernel 上下文 CapBnd=0x1fffffffff）**，机制见 `device_scripts/fixsu.sh` + `root_cmd.sh`：push 命令脚本 → 触发 coredump → 看 root.log。
- 读 root 拥有的 600 权限文件（如 boot_root.log）同理 su 读不了 → 也走 roothelper 或 `kfunc246 show`（memcpy 读内核数据）。

### C3. SELinux Enforcing 时 setuid 完全失效
- **现象**：/system/xbin/su 明明是 rwsr-sr-x，运行后 id 还是 uid=2000。
- **原因**：内核对 setuid-root exec 做 secureexec 检查（域无 `noatsecure` 权限 → 剥夺 euid 提升）。**Permissive 下则不剥夺**。
- **对策**：先保证 Permissive（内核补丁是根治方案），再谈 su。

### C4. grep 的设备侧语法差异
- 设备 toybox grep 不支持某些 GNU 选项（如 `grep -E '->'` 中 `-` 开头模式要转义），报 `invalid option`。
- 对策：`grep -e "pattern"` 或先 `ls -l | awk`。

## D. 内核 / 协议理解类

### D1. 本机 Mali ABI 与文档不符
- DDK 文档/常见资料写的 `PP_START_JOB(0xc1988400)`、`GP_START_JOB(0xc0688500)` 在本机几乎不用；真实流量走 **`0xc0188404` = pp_and_gp_start_job**，24 字节指针信封 `{ctx:u64, *gp_job:u64, *pp_job:u64}`（408/104 字节结构与单发版相同）。
- 信封第 3、4 个 u32 才是 gp/pp 指针（按 u64 对齐取 `w[2]/w[4]`）——按 u32 数组下标猜错曾导致 NULL 解引用崩溃。
- **方法论**：hook 全量 ioctl + 反汇编 dispatch 表（`mali_ioctl` @0xCA34，分支目标经 .rela.text 重定位解析函数名），别信文档。

### D2. 重启后内核态全归零
- slots、core_pattern、SELinux 状态、GPU 绑定全部消失。**每次重启后需要重跑写入链**（rootify 钩子会自动做大部分，失败就手动 30 秒）。
- 验证当前状态的一条命令：
  ```bash
  $A shell "/data/local/tmp/kfunc246 show ffffffc001f613c8 36; getenforce"
  ```

### D3. 输出像素的字节序与采样相位
- GPU 采样输出 u32 的字节序是 `(k2,k1,k0,k3)`（BGRA→RGBA 通道序问题），密集拼装必须重排，否则数据"看起来像乱码"。
- 采样 texel = `sx + 4*px`（**没有** 0.5 像素中心偏移），uv 角点 = `sx/64 + {0,1}`；用 +2 偏移的假设会留下永远采不到的第 0/1 行列（缺口检测会报 uncovered）。

### D4. kallsyms 的行数≠符号数
- 设备 /proc/kallsyms 有 91624 行，但 kallsyms_addresses 数组只有 84092 项（内置符号）；其余 7532 是运行时模块符号。解码脚本按 84092 截断。
- names 区从 0x1b8a200 开始（前面有一段全零填充）；token 表不是标准位置——用"256 个 null 结尾字符串"特征在 names 结束后的 markers 表后面直接扫。

### D5. T50A/T40A 固件包是错误型号
- 用户下载的 "T50A 4999.zip"（MiTVUpgrade_9632.bin）是 **MStar 平台**（Linux 4.9.118）的另一机型，对本机（Amlogic TXL / 3.14.29）毫无用处。**本设备无公开 OTA 包**——所以 system 分区备份是唯一恢复手段，改 /system 前务必确认备份完整。

### D6. /system 重启后回到 ro
- roothelper 里 `mount -o rw,remount /system` 只当次有效。需要写 /system 时每次先 remount（root_cmd.sh 里做）。

## E. 杂项

- **E1** coredump 触发会杀掉当前 adb 会话（kill -SEGV $$ 杀的是主 shell），脚本要能容忍会话断开，触发后重连再收结果。
- **E2** exec-out `su -c 'dd ...'` 的 dd 统计文本走 stderr，但部分 adb 版本会混进 stdout → 产物文件尾部多 99 字节。在 su 命令内加 `2>/dev/null`。
- **E3** NDK clang 在沙箱/权限受限环境找不到 temp 目录 → 同 B1，export TEMP/TMP。
- **E4** `sleep`/循环等待别放在触发 coredump 的同一命令里（会话已死，后面的命令不会执行）——分成"触发"和"收结果"两个 adb 调用。
