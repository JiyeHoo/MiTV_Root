## C. 写原语（**已实机验证 —— 本项目最关键成果**）

### C.1 能力

`gpu_arb_write <phys> <value>`：把一个 8 字节值**重复写满 128 字节**到任意物理地址。
实机证据（原样）：

```
[*] calibration: request 0x800 -> changed [0x800..0x87f], 128 bytes  OK
[*] calibration only - not writing the requested address
```

原理：`MEM_BIND(EXTERNAL_MEMORY, phys)` 把目标页塞进 GPU 页表 → 手搓 PP job 在片元/写回段输出常量 → WB0 单元按 `pixel_format=0x06` 固定输出 **32 像素 × 4 字节 = 128 字节**。

### C.2 已验证的细节

- **128 字节、起点精确**：`pixel_format=0x06` 时请求偏移 `+0x40` 命中 `0x40..0xbc`；`0x09` 只有 16 字节；**没有 4/8 字节粒度**，最小 16 字节；`wh` 字段无效（32 像素突发固定）。
- **可写自己的内存**：`pp_read clear` 模式下魔数 `0xDDCCBBAA00998877` 精确落入 `OUT_VA`（carveout 页 + external 绑定）并被 CPU 读回——说明「GPU 写到我们自己的缓冲」这条线也通。
- **三个必须踩过的坑（已固化进代码注释）**：
  1. PP job 必须置 `user[328] = 1`，否则驱动给 PP reg 0x0 写 `0xFFF00000` 垃圾值 → `UNKNOWN_ERR`；
  2. cmd 缓冲**绝不能全零**：必须有含 `0xBC000000` 终止束的 shader，否则 PP 跑飞立即报错；
  3. WB0 目标页必须用 **CARVEOUT + external** 绑定；用 dma_buf 绑定页做 WB 目标会失败。
- **校验模式**：`gpu_arb_write 0 0`（`phys=0`）只跑自校准、不写目标，可安全反复执行。

### C.3 缓存一致性陷阱（来自 PoC 实测，**执行提权链时必看**）

- **冷数据**（`sys_call_table`、`core_pattern` 等）：GPU DMA 写**立即生效**。
- **热变量**（`selinux_enforcing`、`panic_on_oops` 这类每次权限检查都读的）：GPU 写**无效**，CPU 一直吃自己的 cache，`getenforce` 仍返回 `Enforcing`。
- **所以最后一步必须是 CPU 侧写**：把槽指向 `memcpy` 后用 syscall 244 去写，不能用 GPU 直接写热变量。PoC 作者为此丢过几小时。

## D. 内核侧 job 结构（从 `mali.ko` 反汇编解出，**已证实**）

| 结构 | 布局 |
|---|---|
| PP job（408B，`0xc1988400`） | `[20..112]` = `frame_registers[23]` → PP regs `0x0..0x58`；`[168..220]` = WB0 → PP `0x100..0x12C`；`[400..408]` = 通知指针 |
| GP job（104B，`0xc0688500`） | `[20..44]` = `frame[6]` → GP regs `0x0..0x14`（VSCL_START/END、PLBCL_START/END、PLBU_ALLOC_START/END）；`perf = -1` 跳过；**`plbcl_start == plbcl_end` 时 GP 只跑 VS 不跑 PLBU**（正是「纯数据搬运」想要的模式） |
| PP 寄存器 | `0x0`=FRAME(PLBU 数组)、`0x4`=RSW 指针、`0x30/0x34`=fragment stack、`0x100/0x200/0x300`=WB0/1/2（各 12 字：select/addr/format/downsample/layout/pitch/flags…）、`0x1084/0x10A4`=perf counter |
| GP 寄存器 | `0x0`=VSCL_START、`0x4`=VSCL_END、`0x8/0xC`=PLBCL、`0x10/0x14`=PLBU_ALLOC、`0x20`=CMD（bit0 启 VS、bit1 启 PLBU、bit4 更新 alloc） |

对应 ABI 依据：Amlogic 官方 `mali-driver` 仓库 `utgard/r6p1` 的 `mali_utgard_uk_types.h` / `mali_200_regs.h` / `mali_gp_regs.h`（会话中已逐条核对）。

### 崩溃现场利用（重要方法论）

故意失败的 job 会触发驱动自动 dump 寄存器（dmesg 里 `Executor GP: Job X Timeout` + 寄存器转储）。**GP dump 的 `VSCL_START` 前进了多少字节，就说明命令流执行到第几条**——这是定位「卡在哪条命令」的最强证据，比盲猜快得多。

## E. DDK 用户态逆向（`libGLES_mali.so`，ARM32 / ET_DYN）

| 事实 | 内容 |
|---|---|
| 段布局 | `.text` `0xceb0`+0xf4778；`.rodata` `0x1064e0`+0x15a61；`.data` `0x121000` |
| **GP 命令流构建器 @ `0x8b5c0`** | 7 条命令：`(attr_info_va, 0x20000000\|(na<<17))` → `(out_info_va, 0x20000008\|(nv<<17))` → `(shader_va, 0x40000000\|(ninstr<<16))` → `(attr_count\|(ninstr-1)<<10\|pf<<20, 0x10000040)` → `(0, 0x10000042)`（nv=na=1 时）→ `(0x02000000, 0)`（DRAW num=2）→ `(shader_va, 0x60000000)` |
| **与 Lima 的差异（关键）** | DDK **完全没有信号量命令**（`0x50000000` 全库 0 处命中）；**没有** `UNIFORMS_ADDRESS`、**没有** `UNKNOWN1`；命令顺序也不同。→ **Lima 公开资料的 GP 命令流不能直接用于本机** |
| PP "color-fill" 构建器 @ `0x8b260` 附近 | 其 8-dword PP shader 常量与 PoC **完全一致**（`0xB8000000` / `0xBC000000`）→ **PoC 作者当年就是从这里抄的** |
| PP shader 格式差异 | DDK fill 的 texld 带**内联描述符地址**（`0xE0000000 \| (off>>3)`），与 Lima 的「RSW 纹理数组索引」方案不同 |
| libMali 是否自带可抄的 shader 数据块（本次新查） | **否**。全库 `0xB8000000` 字面量 0 处；`0xBC000000` 仅 1 处（`0x878bc`，落在 `.text`）；`0xB0000000` 1 处（`0x113ad4`，在 `.rodata`）。→ shader 字是运行时用 `movw/movt` 现拼的，**不存在可直接抄字节的 texld shader blob**（除非 hook 运行时） |

## F. 读原语实验矩阵（全部**安全失败**，未触发重启）

目标：让 GPU 把**内核页**的内容搬到我们自己的 ion 缓冲，从而扫出 `sys_call_table`、解出 kallsyms 表。

| # | 路径 | 命令流 / shader | 结果 |
|---|---|---|---|
| 1 | GP | Lima 全套（含 ARRAYS_SEMAPHORE BEGIN/END + UNIFORMS_ADDRESS） | **超时**，`VSCL_START` 只前进 8 字节（跑完第 1 条就卡住），驱动 dump 报 `Job Timeout` |
| 2 | GP | 去掉信号量 | **立即 UNKNOWN_ERR**（无 dump，说明命令流本身非法） |
| 3 | GP | DDK 精确 7 命令序列（`0x8b5c0` 抄来） | UNKNOWN_ERR，输出全零 |
| 4 | GP | DDK 语义 + 共享描述符 + `num=2` + 带操作数的 `0x60000000` | UNKNOWN_ERR |
| 5 | PP | RSW + **Lima ISA** texld shader + 纹理描述符（RGBA8888、Mip0=绑定页、Unnorm Coords） | UNKNOWN_ERR |
| 6 | PP | RSW + **Lima ISA 常量色** shader（无纹理、无 varying） | 未执行（输出 = 清除色） |
| 7 | PP | RSW 全零 + 已验证 job + 常量 shader + 魔数清除色（写自有内存，**对照组**） | ✅ 成功，魔数精确落位 |

**已排除的变量**（都试过，不是原因）：属性/输出描述符布局、WB 目标绑定类型（已改 carveout+external）、`user[328]` 标志、cmd 全零、PP/GP ioctl 号、sampler 字段位偏移（`explicit_lod` 应在 bit17 而非 16、`unknown_2` 应在 bit42 而非 45，已修正）、RSW `first_len`。

**结论**：不是「不可行」，而是**这一代 DDK 的 shader 指令编码未知**；GP/PP 的承载机制（job 提交、WB 回写、绑定）全部工作，缺的是「让 shader 做一次真正的 load→store / texld」的指令字。

## I. 未解问题（下一阶段的靶子）

1. **本机 DDK 时代的 GP/PP shader 指令编码**（Lima ISA 不匹配）：texld 内联描述符 `0xE0000000|(off>>3)` 的偏移基准、指令字序、`ctrl` 头格式。
2. `SHADER_INFO`（`0x10000040`）的位语义：`attr_count | (ninstr-1)<<10 | pf<<20` 各字段在本机是否同义。
3. GP 命令流第 2 条为什么在只跑 VS 时卡死（信号量 vs PLBU 的依赖关系）。
4. 本机 PP 的 `RSW` 机制是否存在（DDK fill 不用 RSW，改用内联描述符），以及 PP 是否真能读任意页。
5. `mali.ko` 里 PP shader 起始地址只在 `job+0x148 != 0` 分支写入（`0x4`=RSW 指针）——该分支的完整条件未完全逆清。
6. 设备实际面板尺寸（43 vs 49）与对应整机型号（L43M5-AA / L49M5-AA），影响找 dump 的目标。
