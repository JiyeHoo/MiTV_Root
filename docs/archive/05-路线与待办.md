# 05 · 路线、替代方案与待办

> 本文回答三个问题：**（1）为什么卡在固件包？（2）不用固件包能不能提权？（3）接下来按什么顺序做？**

---

## 1. 先把「固件包」这件事说清楚

**固件包不是必需品，它只是「最省事的一条路」。**

提权链（`run.sh`）真正需要的只有两样东西：

| 常量 | 用途 |
|---|---|
| `kallsyms_lookup_name` 的**虚地址** | 写进 `sys_call_table[244..259]`，让 `syscall(244,"名字")` 变成符号解析器 |
| `sys_call_table[244]` 的**物理地址** | 写目标本身（= `sys_call_table + 0x7a0 - 0xffffffc000000000`） |

拿到这两个数，剩下的**全部由内核自己解析**（`memcpy`、`selinux_enforcing`、`core_pattern` 都靠 kallsyms 查），整条链 6 个 stage 全是已验证机制，30 分钟内能出 root。

**固件包的作用** = 离线把这两个数算出来。它不是漏洞的前提，而是「在不能读内核内存的情况下，唯一便宜可靠的取数方式」。

所以问题不是「没有固件包就不能提权」，而是：**有没有别的办法把这两个地址弄到手？** 下面逐条评估。

---

## 2. 备选路径评估

| 路线 | 做法 | 成本 | 风险 | 现状 / 判断 |
|---|---|---|---|---|
| **A. 固件 boot.img** | 找 matrix `6.0.1.1275`（显示 `8.8.20.1275`）的 OTA/整机 dump → `vmlinux-to-elf` → 直接读符号 | 用户找包 ~30 分钟；我这边 30 分钟 | 极低 | **最快、最确定**。判别只需 2 分钟（见 [04 §6](04-复现与操作手册.md)）。同平台多面板型号共用 boot，可放宽到 `L43M5-AA`/`L49M5-AA`/`L55M5-AA` 的 ≥ `8.8.20` 版本 |
| **B. 自建 GPU 读原语** | 用同一漏洞让 GPU 把内核页搬到自有缓冲 → 扫描 `.data` 找 16 个连续 `sys_ni_syscall` → `sys_call_table` → 再解 kallsyms 表 | 数小时~数天 | 低（读安全，写才危险） | 承载机制全部打通（job 提交、WB 回写、任意绑定），**只差 DDK 时代 shader 指令编码**。见 §3 的新思路 |
| **C. UART 拆机** | `console=ttyS0,115200`；U-Boot 中断后 `mmc read` boot 分区导出 | 需拆机 + USB-TTL | 中（拆机不可逆） | 备选，用户没表态 |
| **D. 用 AZ dump 反推 1275 地址** | 3 月构建（83951 符号）→ 8 月构建（91624 符号）做函数级 bindiff 猜偏移 | 数天 | **高** | **不建议**：符号数差 7673，插入/删除导致整体漂移；且没有读能力就无法验证任何一个猜出来的地址，猜错=panic |
| **E. 盲写试探 `sys_call_table`** | 在 `.data` 里逐个候选地址写，然后调 syscall 244 看是否命中 | 不可行 | **极高** | 每个错地址都可能 panic，候选空间以 MB 计；**放弃** |
| **F. 其它攻击面** | Amlogic 3.14 内核的其它 CVE、Binder、升级应用、`/dev` 其它节点、adb 本身 | 未知 | 未知 | 完全未调研。作为「路线 A/B 都走不通」时的平行探索，不建议现在投入 |
| **G. 地址泄漏** | 继续挖 dmesg / `/proc` / `/sys` 的指针泄漏 | 低 | 低 | 已挖过：`/proc/modules` 地址为 0，`/sys/module/*/sections` 不可读，dmesg 只泄漏 section 边界和后段锚点。**基本枯竭**，除非出现新接口 |

**结论**：A 与 B 是仅有的两条现实路线，而且**可以并行**——A 依赖用户找包，B 我自己能做。

## 3. 路线 B 的关键下一步（具体到可执行）

上一轮的失败点很明确：**不知道这一代 DDK 的 shader 指令怎么编码**（Lima 公开 ISA 不适用）。

之前一直想「逆向编译器后端」（读 `libGLES_mali.so` 的代码），成本高。**更快的做法是让 DDK 自己把答案吐出来**：

### 方案 B1：在自有进程里跑一次真实 GLES，抓它提交的 job（推荐）

```
写一个 32 位 Android 可执行程序（zig: arm-linux-musleabihf，静态）
 ├─ dlopen("/system/lib/libEGL.so" + "libGLESv2.so")   ← shell 域可加载
 ├─ eglGetDisplay/eglInitialize + pbuffer/surfaceless 上下文（只依赖 /dev/mali，权限 0666）
 ├─ 编译并链接一个极简 shader：
 │     vertex:   attribute vec4 a; varying vec4 v; void main(){ gl_Position=a; v=a; }
 │     fragment: precision mediump float; varying vec4 v; void main(){ gl_FragColor=v; }
 ├─ 触发一次 draw
 └─ 拦截 ioctl(fd, 0xc1988400 / 0xc0688500, job) 的 408/104 字节缓冲 → 原样 dump 到文件
```

拦截方式任选：`LD_PRELOAD` 一个 `ioctl` wrapper（最简单，自己的进程内）、或 `ptrace`。
**拿到的就是本机 DDK 真实生成的 PP/GP job 和 shader 字节**，直接照抄进 `pp_read.c`/`gp_read.c`，绕开整个 ISA 逆向。

风险：低（只用自己的进程和自己的缓冲；`/dev/mali` 本来就 0666）。
唯一不确定：EGL 在没有 SurfaceFlinger 连接的 shell 进程里能否初始化成功（大概率可以，用 pbuffer；不行就退到 `eglCreatePbufferSurface` 或 `EGL_PLATFORM_ANDROID` 的 `ANativeWindow` 方案）。

### 方案 B2：hook 系统里正在跑的 GLES 进程

`surfaceflinger` 天天在走这条路径。但 shell 无权 ptrace 系统进程（SELinux），**不可行**，仅作备选。

### 方案 B3：继续静态逆 shader 编译器

读 `libGLES_mali.so` 里 `__mali_link_binary_shaders` 一类符号，逆后端代码生成。成本高、收益确定，作为 B1 失败后的兜底。

### 本次已排除的一个「抄字节」捷径

原以为 libMali 里会内嵌现成的 texld shader 数据块，直接抄就行。**已核实不存在**：全库 `0xB8000000` 字面量 0 处，`0xBC000000` 仅 1 处且落在 `.text`——shader 字是运行时 `movw/movt` 现拼的。所以只能走 B1（运行时抓）或 B3（逆编译器）。

## 5. 验收标准（root 成功）

1. `adb shell id` → `uid=0(root)`（通过 `su` 或直接 shell）
2. `getenforce` → `Permissive`（或已装 `su` 且可切换）
3. `/system/xbin/su` 存在且 setuid，`su -c id` 返回 uid=0
4. `getprop persist.adb.tcp.port` = 5555（掉线可重连）
5. 重启一次后仍然有效（持久化验证）
6. 回滚脚本可执行（`rm /system/xbin/su`、`setprop persist.adb.tcp.port ""`）

## 6. 决策记录

| 决策 | 理由 |
|---|---|
| 选 root 而非「自定义桌面」 | 用户明确倾向；自定义桌面方案（Aerial 式）不需要 root，但不是用户目标 |
| 走 utgard-lpe 而不是找通用 Android 6 CVE | 该 PoC 与本机驱动/内核/权限条件逐项吻合（r6p1-01rel0、0666 节点、32 位用户态、无 KASLR），且已实测写原语可用 |
| 先做「写」再做「读」 | 写是 PoC 的核心引擎且风险可控（写自有缓冲可验证）；读是新增能力，必须自建 |
| 读原语失败后不急着重写方案 | 已确认承载机制全部正常，失败只在 shader 编码 → 应集中攻这一点，而不是换架构 |
| 不采用「盲写猜地址」 | 错误代价为 panic，候选空间以 MB 计，收益/风险比不可接受 |
